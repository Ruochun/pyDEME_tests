# Trajectory Comparison Across Runs

## Overview

The `compare_trajectory_runs.py` script computes trajectory deviation metrics to quantify stochasticity in DFC (Dense Fresh Concrete) slump test results across multiple simulation runs. This is particularly useful for understanding the impact of GPU arithmetic non-associativity on simulation reproducibility.

## Purpose

When running DEM (Discrete Element Method) simulations on GPUs, slight variations in results can occur due to:
- Non-deterministic floating-point arithmetic operations
- Parallel reduction ordering differences
- Thread scheduling variations

This tool quantifies these variations by comparing particle trajectories across multiple runs, helping you:
1. **Measure stochasticity**: Quantify how much trajectories deviate between runs
2. **Validate reproducibility**: Ensure variations are within acceptable bounds
3. **Compare configurations**: Assess impact of different GPU settings or algorithms

## Metrics Computed

### 1. Average Trajectory Deviation
The mean Euclidean distance between corresponding points along matched particle trajectories.

**Formula**: For matched particles with trajectories sampled at common time points:
```
avg_deviation = mean(||position_baseline(t) - position_run(t)||) for all t
```

**Interpretation**: Lower values indicate more consistent trajectories. This is an absolute measure in simulation units.

### 2. Maximum Trajectory Deviation
The largest point-wise distance observed across all time points and all particles.

**Interpretation**: Shows the worst-case deviation. Useful for identifying outliers or specific problematic time periods.

### 3. Relative Trajectory Deviation (%)
The average trajectory deviation normalized by the average path length traveled.

**Formula**:
```
relative_deviation = (avg_deviation / avg_path_length) × 100%
```

**Interpretation**: 
- This is the **key metric** for assessing simulation reproducibility
- Expresses deviation as a percentage of total motion
- Values < 1% typically indicate excellent reproducibility
- Values 1-5% may be acceptable depending on application requirements
- Values > 5% suggest significant stochasticity that may need investigation

### 4. Path Length Difference
The average absolute difference in total distance traveled by each particle.

**Formula**:
```
path_length_diff = mean(|path_length_baseline(p) - path_length_run(p)|) for all particles p
```

**Interpretation**: Indicates whether particles are traveling similar total distances, even if the exact paths differ.

## Usage

### Basic Usage

Compare multiple runs against a baseline (e.g., run 1):

```bash
python compare_trajectory_runs.py \
    --baseline OUT_slump_V1/particle_trajectories.csv \
    --runs OUT_slump_V2/particle_trajectories.csv \
           OUT_slump_V3/particle_trajectories.csv \
           OUT_slump_V4/particle_trajectories.csv
```

### Using Glob Patterns

If you have multiple run directories following a pattern:

```bash
python compare_trajectory_runs.py \
    --baseline run1/particle_trajectories.csv \
    --runs run*/particle_trajectories.csv
```

### Short Options

```bash
python compare_trajectory_runs.py \
    -b baseline/particle_trajectories.csv \
    -r run2/particle_trajectories.csv run3/particle_trajectories.csv
```

## Input Format

The script expects trajectory CSV files with the following format:
```csv
time,particle_id,x,y,z
0.0,0,1.234,5.678,9.012
0.0,1,2.345,6.789,0.123
0.05,0,1.235,5.677,9.013

```

This format is automatically generated by `pyDEME_DFCSlump.py`.

## Deviation Evolution Plots

In addition to the numerical metrics, the tool automatically generates **deviation evolution plots** for each comparison run. These plots show how the deviation from baseline changes over simulation time for all tracked particles.

### Plot Features

Each plot contains:
- **~50 curves**: One for each tracked particle
- **X-axis**: Simulation time (seconds)
- **Y-axis**: Trajectory deviation from baseline (units)
- **Color coding**: Different colors for each particle (with transparency when many particles)
- **Automatic saving**: Saved as `deviation_evolution_run{N}_{filename}.png`

### Example Plot

![Deviation Evolution Example](deviation_evolution_example.png)

The plot shows:
- How deviation evolves throughout the simulation
- Whether deviation accumulates over time or remains stable
- Individual particle behavior vs. collective trends
- Time periods with higher or lower stochasticity

### Interpreting Deviation Evolution

**Patterns to look for:**

1. **Increasing trend**: Deviation grows over time
   - May indicate accumulation of numerical errors
   - Consider shorter time steps or higher precision

2. **Stable/plateau**: Deviation reaches a steady level
   - Good sign - variations are bounded
   - Stochasticity is manageable

3. **Oscillating**: Deviation fluctuates
   - May reflect physical phenomena (collisions, flow patterns)
   - Normal for complex particle interactions

4. **Outlier particles**: Few curves significantly higher
   - Some particles more sensitive to initial conditions
   - May need investigation of specific particle behavior

### Plot File Naming

Plots are named using the pattern:
```
deviation_evolution_run{N}_{original_filename}.png
```

For example:
- `deviation_evolution_run2_particle_trajectories.png`
- `deviation_evolution_run3_OUT_slump_V2.png`

Files are saved in the current working directory.

## Algorithm Details

### Particle Matching

Particles between runs are matched using the **Hungarian algorithm** (minimum cost bipartite matching) based on their initial positions. This handles cases where:
- Particle IDs may differ between runs
- Initial positions have small variations
- Particles are not in the same order

### Trajectory Comparison

For each matched particle pair:
1. Extract all unique time points from both trajectories
2. Interpolate positions at these time points (linear interpolation)
3. Compute Euclidean distance at each time point
4. Average these distances to get the trajectory deviation

This approach:
- Handles different sampling rates between runs
- Provides a robust measure even with irregular time steps
- Captures the full trajectory behavior, not just endpoints

### Normalization

Relative deviation uses the **baseline path length** as the normalization factor, making the metric:
- Scale-independent (works for different simulation sizes)
- Physically meaningful (fraction of actual motion)
- Easy to interpret across different scenarios

## Best Practices

1. **Use Run 1 as Baseline**: Always use the first successful run as your baseline for consistency

2. **Multiple Comparisons**: Run at least 5-10 simulations to get meaningful statistics on variation

3. **Check Standard Deviation**: Low std dev in relative deviation across runs indicates consistent stochasticity

4. **Document Results**: Save the output for future reference and comparison with different configurations

5. **Context Matters**: Acceptable deviation levels depend on your application:
   - Research studies may require < 1% deviation
   - Engineering estimates might tolerate 2-5% deviation
   - Qualitative studies might accept higher deviations

## Limitations

1. **Assumes Similar Trajectories**: The comparison assumes particles follow roughly similar paths. If simulations diverge significantly (e.g., different final states), metrics may not be meaningful.

2. **Linear Interpolation**: Uses linear interpolation between time points. For highly non-linear motion, more time points may be needed.

3. **Initial Position Matching**: Assumes particles start from similar positions. If initial conditions vary significantly, matching may be suboptimal.

4. **Memory Usage**: Loads all trajectory data into memory. For very large simulations, this may require significant RAM.

## Troubleshooting

### "No matched trajectories"
- Check that trajectory files have the same time range
- Verify that initial positions are similar
- Ensure CSV files are properly formatted

### High deviations with similar-looking results
- May indicate sensitivity to initial conditions
- Check that timestep and parameters are identical
- Consider phase lag effects in oscillatory systems

### Memory errors
- Reduce number of runs compared simultaneously
- Use fewer tracked particles in simulation
- Process runs in batches
